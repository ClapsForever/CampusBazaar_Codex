# Feature Specification: CampusBazaar 校园二手商品交易平台

**Created**: 2026-09-22  
**Status**: Draft (Rev.3 — 状态流转规则修正、终态聊天统一、Mock 验证码流程、重复购买防护、目标平台统一为 HarmonyOS)  
**Input**: User description: "创建完整可运行的 HarmonyOS 手机应用工程 CampusBazaar（包名 edu.fudan.campusbazaar，API 23，ArkTS + ArkUI）。校园二手商品交易平台，第一阶段使用本地 Mock 数据：登录（手机号 + 校园 CAS Mock）、主页面（我是买家/我是卖家/交易提醒）、卖家发布商品（相机/相册照片）、买家浏览（双列卡片、搜索 Panel、智能助手 Panel）、商品详情与购买、交易提醒与交易详情聊天 UI。设计清晰数据模型与 Service 层（预留 AuthenticationService / AgentService 接口）便于后续替换真实 REST API。" + 用户补充约束（同一用户双角色、交易状态机、ID 关联、图片权限处理、页面状态处理、表单校验、验收标准）+ Rev.3 修正（状态流转仅限卖家显式操作、REJECTED/COMPLETED 均为只读终态、Mock 获取验证码流程、重复购买请求防护、目标平台统一为 HarmonyOS 手机）。

## Overview

CampusBazaar 是一个面向校园场景的二手商品交易平台** HarmonyOS 手机应用**（ArkTS + ArkUI，HarmonyOS SDK 6.1.0，API 23）。第一阶段不连接真实后端，所有业务数据使用本地 Mock 数据实现，但通过清晰的数据模型与 Service 层接口抽象（AuthenticationService、AgentService、商品与交易数据服务），使后续可以无缝替换为真实 REST API。「我是买家」与「我是卖家」是同一登录用户的两个功能入口（非两类独立账号），同一用户既可以购买商品也可以发布商品。应用共含 **9 个用户故事**，提供完整的买家浏览/搜索/智能助手/购买请求、卖家发布商品、交易状态流转（卖家显式接受/拒绝/完成）与聊天等端到端闭环体验。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Mock 登录进入主页（含 Mock 验证码流程） (Priority: P1)

用户启动应用后进入登录页，页面提供「手机号登录」和「校园 CAS 登录」两个入口。手机号登录模式：用户输入手机号后可点击「获取验证码」按钮（Mock 阶段不连接真实短信服务，点击后 Toast 提示「Mock 验证码已发送」，任意合法 6 位数字均视为有效验证码），随后输入验证码登录；任意合规输入即可通过 Mock 校验。校园 CAS 登录走 Mock 的 CAS 账号密码流程。任一方式登录成功后进入主页面。

**Why this priority**: 登录是应用的唯一入口，所有后续功能都依赖登录成功后的主页面导航，是 MVP 的必要前提。

**Independent Test**: 启动应用 → 登录页可见两个入口 → 手机号模式完成「获取验证码 → 输入验证码 → 登录」或 CAS 模式完成登录 → 进入主页面。

**Acceptance Scenarios**:

1. **Given** 应用首次启动，**When** 登录页加载完成，**Then** 页面同时展示「手机号登录」与「校园 CAS 登录」两个入口
2. **Given** 用户输入格式合法的 11 位手机号，**When** 点击「获取验证码」，**Then** Toast 提示「Mock 验证码已发送」
3. **Given** 手机号为空或格式非法，**When** 查看「获取验证码」按钮，**Then** 按钮不可用或点击时提示手机号格式错误
4. **Given** 用户在手机号登录中输入格式合法的手机号与 6 位数字验证码，**When** 点击登录，**Then** Mock 校验通过并进入主页面
5. **Given** 用户输入格式非法的手机号（非 11 位数字）或非 6 位数字验证码，**When** 点击登录，**Then** 页面提示格式错误且不跳转
6. **Given** 用户选择校园 CAS 登录，**When** 完成 Mock CAS 流程（任意非空学号/密码），**Then** 登录成功进入主页面

---

### User Story 2 - 主页面三入口导航（同一用户双角色） (Priority: P1)

登录成功后进入主页面。主页面显示两个醒目的主要入口「我是买家」「我是卖家」，同时提供「交易提醒」入口。「我是买家」与「我是卖家」仅代表同一登录用户的两个功能入口，不代表两类独立账号 —— 同一用户既可以购买商品也可以发布商品。点击三个入口分别进入买家页、卖家页、交易提醒页。

**Why this priority**: 主页面是应用的信息架构中枢，承担全部核心功能的分流，并确立「单用户双角色」的核心交互模型。

**Independent Test**: 登录后在主页面点击三个入口，验证各自能正确跳转到对应页面。

**Acceptance Scenarios**:

1. **Given** 用户已登录并位于主页面，**When** 页面加载完成，**Then** 「我是买家」「我是卖家」两个入口醒目展示，且「交易提醒」入口可见
2. **Given** 用户位于主页面，**When** 点击「我是买家」，**Then** 跳转到买家商品浏览页
3. **Given** 用户位于主页面，**When** 点击「我是卖家」，**Then** 跳转到卖家商品管理页
4. **Given** 用户位于主页面，**When** 点击「交易提醒」，**Then** 跳转到交易记录页

---

### User Story 3 - 买家浏览商品（含自己的商品） (Priority: P1)

用户点击「我是买家」进入商品浏览页。商品按照发布时间倒序排列，使用内容社区风格的双列卡片式布局，每张卡片展示商品图片、商品名称、商品价格。商品列表包含当前用户自己发布的商品（可见但不可购买）。页面提供搜索按钮与智能助手按钮。首次启动时预置的带本地图片的 Mock 商品即可完整展示商品流。

**Why this priority**: 商品浏览是买家侧核心价值，是交易闭环的起点。

**Independent Test**: 进入买家页即可验证商品卡片流、排序与布局（含自己发布的商品），不依赖搜索或购买操作。

**Acceptance Scenarios**:

1. **Given** Mock 商品数据已初始化（含预置图片），**When** 用户首次进入买家浏览页，**Then** 商品以双列卡片布局完整展示，每张卡片含商品图片、名称、价格
2. **Given** 存在多个不同发布时间的商品，**When** 列表加载完成，**Then** 商品严格按发布时间倒序排列（最新在前）
3. **Given** 当前用户已发布过商品，**When** 进入买家浏览页，**Then** 自己发布的商品同样出现在列表中
4. **Given** 用户位于买家浏览页，**When** 查看页面工具栏，**Then** 搜索按钮与智能助手按钮均可见

---

### User Story 4 - 商品详情与购买请求 (Priority: P1)

用户在买家浏览页点击任意商品卡片，进入商品详情页。详情页展示商品图片（支持多张）、商品名称、商品描述、商品价格、卖家信息（昵称/头像等）。页面提供「购买」按钮：他人商品点击后弹出确认对话框，确认后创建一条状态为 PENDING（待处理）的 Mock 交易请求并提示成功，该交易随后出现在「交易提醒」列表中；自己发布的商品购买按钮不可用并提示不能购买自己的商品；同一买家对同一商品已存在 PENDING 或 ACCEPTED 状态的交易时，禁止再次创建购买请求并提示「该商品已有进行中的交易」（REJECTED/COMPLETED 历史不阻止重新发起）。

**Why this priority**: 商品详情与购买请求是交易闭环的核心转化环节。

**Independent Test**: 点击卡片 → 查看详情完整性 → 购买 → 确认 → 到交易提醒中可见 PENDING 交易；重复购买被拦截。

**Acceptance Scenarios**:

1. **Given** 用户位于买家浏览页，**When** 点击任一商品卡片，**Then** 进入该商品详情页，完整展示图片、名称、描述、价格、卖家信息
2. **Given** 商品卖家为其他用户，**When** 点击「购买」按钮，**Then** 弹出购买确认对话框
3. **Given** 购买确认对话框已弹出，**When** 用户点击确认，**Then** 创建一条状态为 PENDING 的 Mock 交易记录并提示购买成功
4. **Given** 用户确认购买成功后，**When** 返回主页面进入「交易提醒」，**Then** 新交易（状态 PENDING、当前用户为买家）出现在交易记录列表中
5. **Given** 商品卖家为当前登录用户自己，**When** 查看商品详情页，**Then** 「购买」按钮不可用（置灰）并展示「不能购买自己发布的商品」提示
6. **Given** 当前用户对该商品已存在 PENDING 或 ACCEPTED 状态的交易，**When** 点击「购买」并确认，**Then** 拦截创建并 Toast 提示「该商品已有进行中的交易」
7. **Given** 当前用户对该商品的历史交易为 REJECTED 或 COMPLETED，**When** 点击「购买」并确认，**Then** 允许创建新的 PENDING 交易

---

### User Story 5 - 卖家商品列表与发布商品 (Priority: P1)

用户点击「我是卖家」进入卖家页面，页面展示当前用户已上架的商品列表，并提供「新增商品」按钮。点击后进入商品发布页面，包含商品名称、商品描述、价格、商品照片四个填写项；照片支持调用系统相机拍摄或从系统相册选择图片，最多 3 张，本地阶段使用 URI 保存，需正确处理权限申请、取消授权与取消选择。表单校验规则：商品名称非空、描述非空、价格为大于 0 的合法数值。提交后商品保存到 Mock 商品数据中，并立即显示在卖家商品列表（同时出现在买家浏览页）。

**Why this priority**: 卖家发布商品是平台供给侧的源头，与买家浏览共同构成交易闭环的最小集合。

**Independent Test**: 进入卖家页 → 新增商品 → 填写信息并拍照/选图 → 提交 → 列表立即可见新商品。

**Acceptance Scenarios**:

1. **Given** 用户已登录并进入卖家页，**When** 页面加载完成，**Then** 展示当前用户已上架商品列表与「新增商品」按钮
2. **Given** 用户位于卖家页，**When** 点击「新增商品」，**Then** 进入商品发布页，含名称、描述、价格、照片四项
3. **Given** 用户位于商品发布页且已授予相机权限，**When** 点击「拍摄照片」，**Then** 成功调起系统相机，拍摄完成后照片以 URI 形式回显在表单中
4. **Given** 用户位于商品发布页，**When** 点击「从相册选择」，**Then** 成功调起系统图片选择器，所选图片回显在表单中
5. **Given** 用户未授予相机权限，**When** 点击「拍摄照片」，**Then** 正确发起权限申请；用户拒绝授权时给出友好提示并引导改用相册选择；用户取消选择/拍摄时不报错、表单状态保持
6. **Given** 用户已选择 3 张照片，**When** 再次尝试添加照片，**Then** 提示最多支持 3 张照片
7. **Given** 用户填写完整且合法的商品信息（名称非空、描述非空、价格 > 0），**When** 点击提交，**Then** 商品以 URI 图片保存到 Mock 数据，返回卖家页后新商品立即出现在列表顶部，且买家浏览页同步可见
8. **Given** 名称/描述为空或价格非法（空、非数值、≤ 0），**When** 点击提交，**Then** 表单校验逐项提示错误且不保存

---

### User Story 6 - 搜索 Panel 模糊搜索 (Priority: P2)

用户在买家浏览页点击搜索按钮，页面以 Panel（半模态）形式打开搜索面板，用户输入关键词，系统按商品名称进行模糊匹配，结果实时展示。点击结果卡片可进入对应商品详情。

**Why this priority**: 搜索是浏览的高频辅助手段，但在 Mock 数据规模下非最小闭环必需，列为 P2。

**Independent Test**: 打开搜索 Panel → 输入关键词 → 验证结果仅包含名称匹配的商品 → 点击结果进入详情。

**Acceptance Scenarios**:

1. **Given** 用户位于买家浏览页，**When** 点击搜索按钮，**Then** 搜索 Panel 打开且焦点在输入框
2. **Given** 搜索 Panel 已打开，**When** 用户输入某商品名称的部分关键词，**Then** 结果列表实时展示所有名称中包含该关键词的商品
3. **Given** 搜索关键词无任何匹配商品，**When** 搜索完成，**Then** 展示友好的空结果提示（不白屏）
4. **Given** 搜索结果非空，**When** 点击任一结果卡片，**Then** 关闭 Panel 并进入该商品详情页

---

### User Story 7 - 智能助手 Panel (Priority: P2)

用户在买家浏览页点击「智能助手」按钮，打开智能助手 Panel。用户在输入框输入自然语言商品需求（如「想要一辆二手自行车，预算 200 以内」），系统调用 Mock AgentService 返回模拟搜索结果（商品卡片列表），结果可点击进入商品详情。接口按 AgentService 抽象设计，便于后续接入真实后端 Agent。

**Why this priority**: 智能助手是差异化亮点功能，但第一阶段仅为 Mock 演示，非最小闭环必需，列为 P2。

**Independent Test**: 打开智能助手 Panel → 输入自然语言需求 → 收到 Mock 结果列表 → 点击结果进入详情。

**Acceptance Scenarios**:

1. **Given** 用户位于买家浏览页，**When** 点击「智能助手」按钮，**Then** 智能助手 Panel 打开并展示输入框
2. **Given** 智能助手 Panel 已打开，**When** 用户输入自然语言需求并提交，**Then** 系统通过 AgentService 接口返回 Mock 搜索结果并以商品卡片列表展示（期间展示 loading 态）
3. **Given** Mock 结果列表非空，**When** 点击任一结果卡片，**Then** 关闭 Panel 并进入该商品详情页
4. **Given** 用户提交空内容，**When** 尝试发送，**Then** 不触发请求并提示输入不能为空

---

### User Story 8 - 交易提醒列表 (Priority: P2)

用户在主页面点击「交易提醒」进入交易记录页，页面展示当前用户作为买家和卖家的全部交易记录，每条记录展示商品缩略信息、对手方、交易状态（PENDING/ACCEPTED/REJECTED/COMPLETED）、创建时间。点击任一交易记录进入交易详情页。无交易记录时展示空状态。

**Why this priority**: 交易提醒是交易达成后的协同入口，依赖购买流程先产生交易，列为 P2。

**Independent Test**: 完成一次购买 → 交易提醒中出现 PENDING 记录 → 点击进入交易详情。

**Acceptance Scenarios**:

1. **Given** 当前用户存在买卖交易记录（含预置 Mock 交易），**When** 进入交易提醒页，**Then** 列表展示该用户作为买家与卖家的全部交易记录，含商品信息、对手方、状态、时间
2. **Given** 交易记录列表非空，**When** 点击任一记录，**Then** 进入该交易详情页
3. **Given** 当前用户暂无任何交易记录，**When** 进入交易提醒页，**Then** 展示空状态占位与引导文案

---

### User Story 9 - 交易详情：状态流转与聊天 (Priority: P2)

交易详情页展示交易基础信息（商品信息、买卖双方、状态）。状态流转规则：PENDING → ACCEPTED 与 PENDING → REJECTED 仅能由卖家在交易详情中显式点击「接受」「拒绝」触发；ACCEPTED → COMPLETED 仅能由卖家显式点击「标记完成」触发；系统（含 Mock 自动回复机制）不得自动修改交易状态。交易详情页实现基础聊天 UI：预置交易展示本地 Mock 对话消息；PENDING 与 ACCEPTED 状态下用户可发送消息，发送后系统自动回复一条 Mock 消息（仅追加消息，不改状态）；REJECTED 与 COMPLETED 为终态，仅允许查看历史消息、禁用聊天输入框。无消息时展示空状态。

**Why this priority**: 交易状态流转与聊天是交易达成的履约协同闭环，依赖交易先产生，列为 P2。

**Independent Test**: 打开预置的 PENDING 交易（当前用户为卖家）→ 接受 → 状态变 ACCEPTED → 发送消息收到自动回复；或拒绝 → 状态变 REJECTED 且输入禁用；打开 COMPLETED 交易 → 输入禁用仅可查看。

**Acceptance Scenarios**:

1. **Given** 预置交易中存在当前用户为卖家、状态为 PENDING 的交易，**When** 打开其交易详情，**Then** 展示交易信息与「接受」「拒绝」操作按钮
2. **Given** 当前用户为卖家且交易状态 PENDING，**When** 点击「接受」，**Then** 交易状态变为 ACCEPTED 并提示成功，聊天可正常进行
3. **Given** 当前用户为卖家且交易状态 PENDING，**When** 点击「拒绝」，**Then** 交易状态变为 REJECTED，聊天输入框禁用
4. **Given** 当前用户为卖家且交易状态 ACCEPTED，**When** 点击「标记完成」，**Then** 交易状态变为 COMPLETED，聊天输入框禁用
5. **Given** 交易详情页已加载预置 Mock 消息，**When** 查看聊天区域，**Then** 消息按时间排列、区分买卖双方气泡
6. **Given** 交易状态为 PENDING 或 ACCEPTED，**When** 用户在输入框输入消息并点击发送，**Then** 消息立即追加到对话列表，随后系统自动回复一条 Mock 消息，且交易状态保持不变
7. **Given** 交易状态为 REJECTED 或 COMPLETED，**When** 查看交易详情，**Then** 仅展示历史消息，聊天输入框禁用不可发送
8. **Given** 交易尚无任何消息，**When** 打开其交易详情，**Then** 聊天区域展示空状态提示
9. **Given** 当前用户为买家，**When** 查看任一状态交易详情，**Then** 不展示「接受/拒绝/标记完成」按钮（状态操作仅卖家可用）

---

### Edge Cases

- 搜索/智能助手无匹配结果时：展示友好空状态提示（含引导文案），不白屏
- 买家/卖家商品列表为空时：展示空状态占位（如「暂无在售商品，点击新增商品上架」）
- 交易列表为空、交易聊天无消息时：展示空状态占位与引导文案
- 手机号格式非法（非 11 位数字）时「获取验证码」不可用或提示格式错误；验证码非 6 位数字时登录即时校验提示，不发起登录
- 相机权限被拒绝时：给出提示并引导用户改用相册选择图片；用户取消拍摄/取消选择时：不报错、表单已选照片状态保持
- 商品发布表单：名称为空、描述为空、价格非法（空/非数值/≤ 0）分别给出明确校验提示
- 照片数量达到 3 张上限后再次添加：提示「最多支持 3 张照片」
- 购买自己发布的商品：详情页购买按钮禁用并提示「不能购买自己发布的商品」
- 重复购买请求：同一买家对同一商品存在 PENDING/ACCEPTED 交易时再次购买被拦截并提示「该商品已有进行中的交易」；REJECTED/COMPLETED 历史不阻止重新发起
- 交易状态操作权限：非卖家触发接受/拒绝/完成、或终态（REJECTED/COMPLETED）交易再次流转：Service 层拒绝，UI Toast 提示
- 页面数据加载期间展示 loading 态；所有列表/面板在空态与异常输入下均不能出现白屏或应用异常退出
- Mock 阶段网络/后端不可用场景不存在（全部本地实现），但 Service 层需以异步方式返回数据，模拟真实 API 调用形态

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供登录页，包含「手机号登录」与「校园 CAS 登录」两个入口，登录成功后进入主页面
- **FR-002**: 手机号登录模式必须提供「获取验证码」按钮：手机号格式合法（11 位数字）时可点击，点击后 Toast 提示「Mock 验证码已发送」（Mock 阶段不连接真实短信服务）；登录时必须校验手机号格式与 6 位数字验证码格式，任意合法 6 位数字验证码均通过（页面需有 Mock 提示文案）
- **FR-003**: 校园 CAS 登录必须以 Mock 流程实现（任意非空学号/密码），并预留 AuthenticationService 接口，后续可替换为真实手机号认证与复旦 CAS 认证
- **FR-004**: 主页面必须醒目展示「我是买家」「我是卖家」两个主要入口，并提供「交易提醒」入口；「我是买家」与「我是卖家」为同一登录用户的功能入口（同一用户可购买也可发布商品）
- **FR-005**: 买家浏览页必须以双列卡片布局展示商品，每张卡片含商品图片、名称、价格，商品按发布时间倒序排列；列表必须包含当前用户自己发布的商品（可见但不可购买）；首次启动必须通过预置带本地图片的 Mock 商品完整展示商品流
- **FR-006**: 买家浏览页必须提供搜索按钮；点击后以 Panel（半模态）形式打开搜索面板，支持按商品名称模糊搜索，结果实时更新，点击结果可进入商品详情
- **FR-007**: 买家浏览页必须提供「智能助手」按钮；点击后以 Panel 形式打开智能助手面板，用户输入自然语言商品需求后，系统通过 AgentService 接口返回 Mock 搜索结果（商品卡片列表），点击结果可进入商品详情；AgentService 接口设计必须便于后续接入真实后端 Agent
- **FR-008**: 点击商品卡片必须进入商品详情页，完整展示商品图片（支持多张）、名称、描述、价格、卖家信息
- **FR-009**: 商品详情页必须提供「购买」按钮；卖家为他人时点击后弹出确认对话框，确认后创建一条状态为 PENDING 的 Mock 交易记录并提示成功；卖家为当前用户时购买按钮必须禁用并提示「不能购买自己发布的商品」；同一买家对同一商品已存在 PENDING 或 ACCEPTED 状态的交易时必须禁止创建并提示「该商品已有进行中的交易」（REJECTED/COMPLETED 历史不阻止新请求）
- **FR-010**: 卖家页必须展示当前用户已上架的商品列表，并提供「新增商品」按钮进入商品发布页
- **FR-011**: 商品发布页必须包含商品名称、商品描述、价格、商品照片四个表单项；照片必须支持调用系统相机拍摄或从系统相册选择，最多 3 张，本地阶段以 URI 形式保存；必须正确处理相机权限申请、拒绝授权与取消选择/拍摄场景；表单校验必须包含：商品名称非空、描述非空、价格为大于 0 的合法数值，校验失败逐项提示且阻止提交
- **FR-012**: 商品发布提交成功后必须保存到 Mock 商品数据，并立即显示在卖家商品列表与买家浏览页（发布时间倒序置顶）
- **FR-013**: 交易提醒页必须展示当前用户作为买家和卖家的全部交易记录，每条记录含商品信息、对手方、交易状态（PENDING/ACCEPTED/REJECTED/COMPLETED）、创建时间
- **FR-014**: 交易详情页必须展示交易基础信息（商品、买卖双方、状态）；状态流转仅能由卖家显式操作触发：PENDING 时可「接受」（→ ACCEPTED）或「拒绝」（→ REJECTED），ACCEPTED 时可「标记完成」（→ COMPLETED）；REJECTED 与 COMPLETED 为终态不可再流转；当前用户为买家时不展示状态操作按钮；系统与 Mock 自动回复机制不得自动修改交易状态
- **FR-015**: 交易详情页必须实现基础聊天 UI：预置交易使用本地 Mock 消息展示对话；PENDING 与 ACCEPTED 状态下用户可发送消息，发送后系统自动回复一条 Mock 消息（仅追加消息、不改状态）；REJECTED 与 COMPLETED 终态下禁用聊天输入、仅可查看历史消息；无消息时展示空状态
- **FR-016**: 所有业务数据必须通过 Service 层接口访问（认证、商品、交易、消息、智能助手）；User、Product、Transaction、Message 等 Mock 数据必须通过 ID 建立明确关联（如 Product.sellerId → User.id、Transaction.productId/buyerId/sellerId → 对应实体、Message.transactionId → Transaction.id）；Service 以异步方式返回数据模拟真实 API 形态，后续可在不改动页面层的前提下替换为 REST API 实现
- **FR-017**: 工程必须使用 ArkTS + ArkUI 实现，遵循 HarmonyOS HIG，代码按 pages / views / components / viewmodel / model / service / data / common 分层组织（对应"pages、components、models、services"的分层要求），避免业务代码集中在单个页面
- **FR-018**: 工程必须生成必要的路由（页面注册）与资源文件（图标、Mock 商品占位图、字符串等），保证工程可独立编译运行
- **FR-019**: 所有页面必须正确处理基础的 loading、empty、error 状态，至少覆盖：无商品、搜索无结果、无交易、无消息、表单校验失败等场景，任何场景下不得出现白屏或应用异常退出

### Key Entities *(include if feature involves data)*

- **User（用户）**: 平台用户，含 id、昵称、头像、联系方式（手机号/学号）；当前登录用户在 Mock 数据中固定为一个预置账号，同时预置若干其他用户（作为商品卖家/交易对手方）；同一用户兼具买家与卖家角色
- **Product（商品）**: 二手商品，含 id、名称、描述、价格、图片列表（拍照/相册选择的图片 URI；预置商品使用内置资源图）、发布时间、sellerId（关联 User）、上架状态
- **Transaction（交易）**: 一次购买请求产生的交易记录，含 id、productId、buyerId、sellerId、创建时间、状态；状态模型包含 PENDING（买家已发起、待卖家处理）、ACCEPTED（卖家已接受）、REJECTED（终态，卖家已拒绝）、COMPLETED（终态，交易完成）；状态流转仅能由卖家显式操作触发（PENDING→ACCEPTED/REJECTED，ACCEPTED→COMPLETED），系统不得自动流转；同一买家对同一商品同时最多存在一笔进行中（PENDING/ACCEPTED）交易
- **Message（聊天消息）**: 交易详情内的对话消息，含 id、transactionId（关联 Transaction）、senderId（关联 User）、消息内容、发送时间；Mock 阶段预置对话并由本地逻辑生成自动回复（自动回复仅追加消息，不改变交易状态）

- **SC-004**: 搜索 Panel 与智能助手 Panel 均 100% 可正常打开与关闭；搜索结果准确包含所有名称匹配商品；智能助手稳定返回 Mock 结果列表

## Assumptions

- 第一阶段无真实后端：全部业务数据为内存 Mock 数据（应用重启后恢复初始 Mock 状态，不持久化到磁盘）；Mock 数据间通过 ID 关联，Service 层接口与真实 REST API 形态对齐
- 不做登录态持久化：每次启动应用都从登录页开始
- Mock 登录规则：手机号需为 11 位数字格式，「获取验证码」点击后 Toast「Mock 验证码已发送」（无真实短信），验证码输入任意 6 位数字即可通过；CAS 登录输入任意非空学号/密码即可通过（页面上有明确的 Mock 提示文案）
- 单一当前用户 + 双角色：Mock 预置一个「当前用户」及若干其他用户；买家列表包含自己发布的商品但不可购买（按钮禁用 + 提示）
- 预置 Mock 商品：首次启动即包含若干条带本地资源图片的商品（由其他用户及当前用户发布），保证买家商品流完整展示
- 预置 Mock 交易：至少覆盖「当前用户为卖家的 PENDING 交易」（验证接受/拒绝）、「当前用户为买家的 ACCEPTED 交易」（含预置消息，验证聊天）、「COMPLETED 交易」（含预置消息，验证终态只读）；REJECTED 状态由用户执行拒绝操作产生
- 交易状态流转严格由卖家显式操作触发；Mock 自动回复仅追加聊天消息，不修改交易状态
- 聊天可用状态：PENDING 与 ACCEPTED 可发送消息；REJECTED 与 COMPLETED 为只读终态（输入禁用，仅查看历史）
- COMPLETED 流转：由卖家在 ACCEPTED 状态的交易详情中点击「标记完成」触发
- 重复购买防护：同一买家对同一商品存在 PENDING/ACCEPTED 交易时禁止再次创建购买请求（提示「该商品已有进行中的交易」）；REJECTED/COMPLETED 历史不阻止重新发起
- 商品照片最多 3 张（相机一次拍一张，可多次拍摄；相册可多选），本地以 URI 形式保存；权限申请、拒绝授权、取消选择均有友好处理
- 智能助手 Mock 逻辑：对输入的自然语言做关键词匹配，返回命中的 Mock 商品列表与预设话术；真实 Agent 由后续后端提供
- 第一阶段不实现：商品下架/编辑/删除、支付、真实消息推送、个人中心、登录态持久化
- 目标环境：HarmonyOS 手机（HarmonyOS SDK 6.1.0，API 23），允许正常使用 HarmonyOS Kit（如 @kit.CameraKit、@kit.MediaLibraryKit）；最终验收以 HarmonyOS API 23 模拟器能够成功编译、安装并运行为标准
