审查日期：2026-10-23（北京时间）  
发布目标：上架应用市场，向真实用户开放（用户已确认）  
审查对象：当前工作区源码、三份 `2026-10-18-draft-3` 草案、既有发布清单与部署记录。

**结论：三份草案可以作为正式版的基础，但当前还不具备直接提交公开发布的条件。应先确定运营事实，补齐可实际执行的产品与运营流程，再据实定稿。去掉“草案”和替换占位符，不能解决目前的发布缺口。**

本次是文件、源码与公开规则的交叉审查。未登录云服务器、应用市场控制台或模型采购账号，未完成真机抓包；涉及现网状态、资质、供应商合同的结论仍须负责人核验。下文 P0 是本项目建议采用的发布阻断等级，不表示所有事项都是相同性质的法定义务。

### 2.1 身份与主体：需要先解决，不能只调整措辞

项目已有商品发布和交易内文字通讯。《移动互联网应用程序信息服务管理规定》第六条对这类服务规定了真实身份信息认证要求。因此，“用户自行保证邮箱真实”不足以支撑当前公开发布方案。可以评估经核实可满足要求的手机号认证或其他合法认证服务，采用后台核验、前台昵称展示；无需因此公开用户的证件或手机号。[官方规定](https://www.cac.gov.cn/2022-06/14/c_1656821626455324.htm)

同时需要评估项目作为网络交易平台的主体、卖家核验及其他配套义务。平台经营主体的要求，与平台内个人出售闲置物品是否需要市场主体登记，是两件不同的事。产品目前提供商品浏览、撮合、订单与交易消息，不能仅因线下付款就直接排除平台规则。若认定适用，还应核对经营者识别、公示、信用评价、信息留存和依法报送等事项，不能一律排到发布之后。[电子商务法](https://www.samr.gov.cn/zfjcj/tzgg/art/2023/art_d337c3291e8b40459ca03dea54395856.html)、[2025 年修正的网络交易监督管理办法](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2025/art_4b47c79b8d994a42bba4835997688faa.html)

学校归属也需要单独处理：`store.ts:64` 给注册用户统一分配配置中的学校 ID；邮箱不限域名。这不构成校内准入控制。若首版宣称“仅本校”或“同校交易”，须有相应的归属和准入方案；尚未建立时，应调整页面承诺和隐私政策中的实际受众描述。

### 2.2 注销与投诉：可以采用人工处理，但必须真正可用

不一定要先开发复杂工单平台。可先实现 App 内可发现的申请/反馈入口，由指定人员按流程处理，后台保留操作和反馈记录；是否满足目标应用市场的具体审核方式，还要在提交前核实。仅写“联系项目组”但不给渠道，或者仅增加按钮但后台无人执行，都不算完成。

注销方案应明确进行中交易、争议证据、照片、交易对方的记录、AI 历史与备份分别如何处理。不得承诺注销立即删除所有数据，也不能以有过交易为由永久拒绝注销。对于需要依法保留的对象，须确定具体依据、期限和使用限制。[网络数据安全管理条例第二十一至二十四条](https://app.www.gov.cn/govdata/gov/202409/30/520076/article.html)

### 2.3 AI：同时涉及提问者与商品发布者

当前数据流：

1. App 将问题发送给业务 API；API 将账号及学校上下文传给项目 Agent。
2. Agent 的需求理解请求包含本轮问题、此前筛选条件、**此前需求摘要 `previousNeeds`**、上次展示商品的标题与顺序、分页信息。
3. 结果表达请求包含问题、需求、筛选条件及工具结果。工具结果包括商品描述和图片访问链接；详情可包括卖家昵称和发布时间。
4. 业务 SQLite 保存成功轮次；Agent 另有内存会话及请求结果缓存。删除数据库历史尚未联动清除这些内存与第三方记录。

代码依据：`backend/agent/src/agent/service.ts:73`、`:145`、`:179`，`backend/agent/src/contracts/index.ts:107`，`backend/agent/src/sessions/store.ts:34`，`backend/api/src/store.ts:448`。

建议优先去掉模型输入中的非必要图片 URL、卖家昵称，评估描述中见面地点与联系方式的过滤；商品卡片仍可由业务接口显示图片，不要求把图片地址提供给模型。是否采用这些调整，需要按实际找货效果验收。模型收到可读取链接，不等于已证实供应商实际下载过图片。

不能只取得提问者的一个“使用 AI”勾选，就当然处理卖家的个人信息。发布者应得到相应告知，数据处理依据及必要同意应按实际关系落实；同样，单独的 AI 提示框不能代替供应商合同与影响评估。

可核实的公开信息已有一部分：DeepSeek 现行公开政策列明主体为杭州深度求索人工智能基础技术研究有限公司及其关联公司，联系邮箱为 `privacy@deepseek.com`，并涉及 API 和输入输出用于训练的安排。但**本项目具体 API 账号的合同、退出机制及执行情况尚未核验**，不能据此直接承诺“本应用数据绝不训练”或把 DeepSeek App 中的设置写成校园集市已有能力。[DeepSeek 官方隐私政策](https://cdn.deepseek.com/policies/zh-CN/deepseek-privacy-policy.html)

当前界面有“AI 找物”标题，但未见草案计划的回复附近“AI 生成，仅供参考”提示。应核对适用的显式、隐式标识及后续复制/导出功能；商品上传也应评估用户发布生成合成内容的标识场景。清除照片位置等 EXIF 时，注意识别和保留依法需要的生成合成标识。[人工智能生成合成内容标识办法](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)

2026 年网信办公告明确，直接调用已备案模型的应用或功能存在由地方网信办开展登记的路径，并要求上线应用公示所用服务情况。项目应按实际功能向属地核实适用程序，不能用模型供应商的备案替代本应用需完成的手续。若相关条件来不及完成，可把暂缓开放 AI 作为首版范围的一个决策选项；采取这一方案需同步关闭实际入口/API 能力并修改三份文件及商店介绍。[网信办 2026 年公告](https://www.cac.gov.cn/2026-09/14/c_1791136833136332.htm)

## 3. 三份正文分别如何修改

### 3.1 用户协议

建议保留目前的主要结构，完成以下调整：

1. 补齐真实主体、适用地区、发布日期与生效日期、联系方式、服务对象和年龄方案。
2. 用最终落地的注册/认证、账号恢复、注销、投诉、申诉方案替换测试说明及待办。
3. 修正第二节第 3 项的过期描述：当前已支持买家主动取消，不能继续列为未实现功能。
4. 交易完成继续明确为卖家“标记完成”；确定误操作及争议反馈方式，避免把状态当作付款或验收证明。
5. AI 部分据最终数据流、供应商和界面标识定稿，补充适用的使用与标识规范。
6. 明确交易规则与用户协议的关系、可查阅方式及版本，不必机械增加三个注册必勾框；首次发布或预约时可增加相关重点提示并保留记录。
7. 对重大责任、公开范围、终止服务等条款进行明显提示；避免“最终解释权归平台”“线下交易概不负责”等表达。
8. 删除面向项目组的开发待办段落，把它们保留在内部清单；前提是已完成对应事项或实际移除该功能。

**现在即可采用的一处修正文案：**

> 当前版本未提供评价、在线仲裁、平台内退款、商品发布后编辑、账号自助注销及邮件找回密码等完整流程。买卖双方可取消待确认或待交易的交易记录；取消仅改变应用中的交易状态，不执行退款，也不当然解决双方的合同争议。

这段仅用于纠正当前草案的功能矛盾；正式版仍需替换为发布时实际可用的注销与争议方案。

### 3.2 隐私政策

现有按功能说明可保留，但正式版应把不确定事项落实为事实，并增加便于核对的清单：

| 要形成的内容 | 必须回答的问题 |
| --- | --- |
| 个人信息收集清单 | 每个功能收什么、何时收、为什么收、是否必要、不提供会怎样、如何停止 |
| 第三方与接收方清单 | 实际法律主体、数据种类、目的和方式、处理关系、政策与联系渠道；包括服务端云服务和模型 API |
| 保存期限表 | 每类数据的期限或明确确定方法、起算点、到期处置、例外、备份覆盖及执行人 |
| 权益办理说明 | 查阅复制、更正、删除、撤回同意、注销等入口、核验方式、反馈时限与复核方式 |
| 系统能力与权限说明 | 区分系统选择器访问所选文件与申请整个相册/相机权限，保持与正式包一致 |

具体要核实和修正：

- 加入最新 AI 需求摘要及实际外发字段；如果完成最小化改造，按改造后的结果写。
- 保留“选择图片不代表读取整个相册”等准确说明，别为迎合模板虚构定位、通讯录或统计 SDK。
- 核实阿里云、腾讯云旧入口、两处迁移归档、备份及运维副本的实际地域与生命周期；云品牌、IP 或历史部署说明不能替代这一核实。
- 对公开商品内容、卖家资料和图片链接的可见范围作清楚提示，并按实际处理依据落实授权；必要的单独同意不能由普通注册勾选概括替代。[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)
- 将“内部测试建议使用独立密码”等内容换成正式安全说明；只有真实 HTTPS 和安全措施完成后，才能更改现状描述。
- 不照抄其他平台的期限、第三方列表和“15 个工作日”等承诺；响应标准需结合适用要求及团队实际能力确定。

### 3.3 社区与交易规则

现有发布要求、禁售清单、线下验货与防诈骗内容可作为基础，正式版重点补齐：

- 商品及账号准入条件：个人闲置与经营性卖家如何识别、哪些品类首版允许、受限品类如何阻断和处置。
- 交易操作及后果：占用商品、接受、拒绝、双方取消、卖家标记完成、终态聊天关闭；是否设置超时释放需先做产品决定并实现，不能只写入文本。
- 缺陷披露与退换争议：区分真实约定、法定责任及平台协助范围，不承诺一律不退或一律支持无理由退货。
- 举报入口、受理材料、处理步骤、紧急处置、反馈时限、处置理由及人工复核。
- 已完成/取消的交易仍能发起争议反馈；不强求必须重开普通聊天，但应保留维权通道。
- 侵权通知和反通知、必要证据保存、诈骗及危险情况的升级处理。
- 收费与服务边界：首版免费就据实写，后续收费先告知并按适用程序修改规则。

**上线前必须决定的交易方案：**保留卖家单方标记完成，还是增加买家确认。两种方案的产品复杂度不同；买家确认并非所有线下交易记录工具都必须有的统一按钮要求。但若保留单方标记，应清楚说明含义、提供纠错与争议入口，且不能据此剥夺买家权利。

## 4. 现有发布清单需要更新的地方

1. “决定正式是否需要买家取消”已过时：前后端现已支持双方取消，应改成验证现有权限、状态和提示是否一致。
2. 图形验证码是防滥用的一种技术选项，恢复它不是所有 App 的统一发布前提。应先确认所选认证、注册限流及风险控制方案，避免投入后仍未解决真实身份问题。
3. 只保存注册版本不能覆盖后续规则变更。`registration_consents` 以 `user_id` 为主键，目前没有多次接受事件结构；登录也未检查当前版本。需补充可追溯的事件记录与旧文本归档。
4. 应增加适用的 2026 年《网络交易平台规则监督管理办法》要求；该办法已于 2026-02-01 施行。适用时需覆盖首页显著入口、规则检索、完整阅览下载、意见征集、公示安排、历史版本及处置申诉，不能只保留“提前七日”一句；重要情形另有十五日等要求。当前 `LegalDocument.ets` 仅展示一个可复制的纯文本页面，未见检索和历史版本入口。[官方办法第七至十九条](https://www.samr.gov.cn/wljys/gzzd/art/2026/art_74b094e2fda240cbada023e223bc25bb.html)
5. 增加应用市场材料的一致性验收：App 内、公开链接、隐私标签、权限声明、商店介绍、客服渠道、实际代码行为保持一致。
6. AI、云服务和隐私政策正文不能只改内容不换接受版本。发布时保存本次正式正文快照和校验值，明确适用用户及版本迁移策略；并非每次排版修订都必须重新同意，需按实质变化判断。

| 交易模式 | 保留线下验货、付款、交付，首版无平台支付、托管和物流 | 三份文件统一，页面不出现资金担保或已验证付款的暗示 |
| 账号认证 | 保留邮箱登录与否可选，但信息发布/通讯的认证义务必须有对应方案 | 新增认证字段、供应商、权限和留存时同步更新隐私告知 |
| AI | 确认本次是否保留；保留则完成数据、标识与适用程序 | 暂缓 AI 需要实际关闭能力，同时清理对外功能描述 |
| 客服与权益 | 采用 App 入口加人工办理可作为起步方案 | 明确人员、核验与执行步骤，验证真实请求能办结 |
| 交易完成 | 选定单方标记或双方确认 | 写清状态含义、纠错渠道及完成后的争议处理 |

无须为了写正式协议而强行接入支付、托管或物流。应先把确定提供的服务做完整，并核对适用平台义务。

## 6. 数据留存需要负责人逐项定案

| 数据对象 | 源码能确认的当前状态 | 发布前要确定并执行 |
| --- | --- | --- |
| 账号、邮箱、资料及未来认证数据 | 账号持续保存；可改昵称、头像和密码 | 使用期间、注销后的具体处理；认证原始材料与核验结果分开最小化管理 |
| 商品、头像及商品图片 | 支持商品下架；旧头像与未发布图片未见完整清理 | 公开停止时点、争议保留对象、闲置文件期限、链接撤销与关联副本处理 |
| 交易及消息 | 持续保存；交易终态后消息只读 | 如适用电商法第三十一条，落实交易完成起不少于三年的必要信息留存；不得扩张成所有数据统一保存三年 |
| AI 历史与 Agent 内存 | 历史可手动删；内存按默认 24 小时闲置期限失效并按请求清扫 | 默认留存策略、主动删除联动内存/缓存、供应商和备份处置；不要把 24 小时当作历史删除期限 |
| 会话、限流、幂等及同意记录 | 会话有效期七天；部分限流按请求触发清理；其他对象未见完整保留方案 | 分别定期限及必要留痕，区分不可再用和实际删除 |
| 日志、备份、旧服务器迁移副本 | 部署文档说明存在两台服务器上的旧副本 | 实际地域、访问权限、保存与覆盖周期、恢复后重新执行删除/限制的机制 |

以上是待定事项，不应把“未确定”原样作为正式政策。若确实难以给出固定期限，应给出明确确定方法，并有可执行的内部管理依据。
