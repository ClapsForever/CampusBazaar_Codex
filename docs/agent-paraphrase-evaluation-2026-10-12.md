# Agent 商品查找改写评测（2026-10-12）

本文件保留修复前的评测记录。问题已修复并部署，最终 53 个主场景、20 个新增改写及 6 个诊断场景全部通过，详见[修复与验收报告](agent-paraphrase-fix-2026-10-12.md)。

已复现“同一需求换一种说法就不能正确执行”的问题。53 个场景完整执行两轮：已有能力的 48 个场景第一轮通过 30 个，第二轮通过 29 个；其中 18 个场景两轮均失败。另有 5 个扩展需求两轮均未完成。很多失败发生在模型已经给出正确计划之后，服务端规则删掉了条件或覆盖了计划。

这是本次特定商品集和问法集的结果，不能当作所有用户请求的总体准确率。

## 方法与范围

- 使用 licx 当前部署版本的 Agent、真实 `deepseek-chat` 模型、真实 `HttpBusinessClient` 和当前业务 API 查询实现。Agent 源码指纹与本地项目一致。
- 业务 API 在独立进程中使用内存 SQLite，只监听随机回环端口。29 件商品及账号均为合成数据，不打开线上数据库，不写真实对话历史。
- 主评测共 53 个场景，执行两轮；另执行 6 个诊断场景。7 类前置对话先由真实模型执行，成功后复制会话条件、展示顺序和页码，供各个追问独立测试。
- 判定检查实际查询条件、工具调用、推荐商品 ID、返回状态和会话页码。不会把“已帮你筛选”这样的回复当成成功证据。
- 商品以元标价、接口以分传递。键盘样本价格分别为 40、80、120 元；同一校内，分布于邯郸、江湾、张江校区，成色分别为八成新、九成新、全新。另有教材、耳机等商品及 14 件用于验证翻页的中性笔。
- 保持运行配置 `MAX_RESULTS=10`、每轮超时 60 秒、模型温度 0。测试最多并发两轮，共 218 次模型请求。没有模型或后端请求报错、超时；失败均为本次任务行为未满足判定。
- 测试不重启或重载服务。测试前后 licx API/Agent/Nginx 和队友 API/Agent 的 PID、启动时间均相同，全部 active。

第一轮北京时间 20:16:31–20:17:20；第二轮 20:18:45–20:19:39。诊断复核的精确时间及被测编译文件 SHA-256 保存在诊断 JSON 中。

## 稳定复现的问题

### 1. 口语和英文预算被丢弃（优先级 P1）

| 说法 | 实际结果 |
| --- | --- |
| 帮我找50元以内的键盘 | 正确，只返回 40 元键盘 |
| 键盘，预算五十元以内 | 正确，只返回 40 元键盘 |
| 想收个键盘，别超过五十块 | 返回 40、80、120 元键盘，未应用预算 |
| 键盘有吗？我就五十块预算 | 返回 40、80、120 元键盘，未应用预算 |
| 键盘不要超过50块钱 | 返回 40、80、120 元键盘，未应用预算 |
| Find a keyboard under 50 yuan | 返回 40、80、120 元键盘，未应用预算 |
| Please find an English book under 50 yuan | 返回 35 元和 90 元教材，未应用预算 |

失败例中，计划模型都已输出 `maxPriceCents: 5000`。`mergeSearchFilters` 的金额依据检查只接受有限词语、单位和数字组合，“块”“yuan”等表达未通过检查，预算随后被删除。问题位于 Agent 条件合并，不是商品库存缺失，也不是模型没理解金额。

对应场景：`search-02`、`search-03`、`search-06`、`search-10`、`price-03`。

### 2. 明确保留的预算在换商品时消失（优先级 P1）

前置查询为“找50元以内的键盘”，追问“不买键盘了，改找耳机，预算仍然50元”。模型正确输出耳机与 5000 分上限，但实际筛选里没有预算，返回了 70 元耳机。

本地对同一计划的确定性复核显示：旧解析器先匹配了句子中被否定的“键盘”，把它视为类别变化，清除了旧预算；“预算仍然50元”又未匹配金额更新规则。条件合并随后用这个不完整的解析结果删除模型已经正确给出的预算。

对应场景：`switch-category`。

### 3. 取消和放宽条件过度依赖固定说法（优先级 P2）

| 前置条件 | 能执行的说法 | 不能执行的等义说法 |
| --- | --- | --- |
| 预算上限 50 元 | 取消预算限制 | 不看价格了／多少钱都行／把价格上限去掉 |
| 只看全新 | 不限成色 | 新旧都可以 |
| 只看江湾校区 | 不限校区 | 在哪个校区都行 |
| 只看江湾校区 | 首次查询时“最好在江湾”能作为偏好 | 江湾优先，其他校区也可以：仍保留江湾硬条件 |

这些失败例的计划模型正确给出了对应字段的 `null` 或校区偏好，但服务端不认可等义取消表达。结果通常变成“请明确要调整的条件”，或继续只返回江湾商品。

对应场景：`cancel-price-02/03/04`、`cancel-quality-02`、`cancel-campus-02`、`soften-campus`。

### 4. 成色理解和实际后端语义不一致（优先级 P2）

“找全新键盘”正确返回全新商品；“想找没用过的键盘”虽然模型同样输出 `condition: new`，服务端却删掉成色，返回了三个不同成色的键盘。原因是成色依据检查不认识“没用过”。对应 `quality-02`。

“找九成新以上的键盘”只返回九成新的机械键盘，漏掉全新的罗技键盘。真实 API 对 `condition` 使用等值查询，Mock 后端却使用成色等级大于等于。现有 Mock 测试不能反映真实 API 的这个差异。对应 `quality-03`。

### 5. 模型的翻页计划被代码覆盖（优先级 P2）

14 件中性笔的第一页有 10 件，第二页有剩余 4 件。“下一页”和“换一批”正确；“还有其他的吗？”“第二页”被要求补充筛选条件；“继续”重复返回第一页。

三个失败例中模型都已输出 `page: 2`。执行逻辑没有采用该页码，而是再次通过固定关键词和仅支持阿拉伯数字的页码正则决定是否翻页；“继续”虽通过无变化检查，却被重置为第一页。

对应场景：`page-03/04/05`。

### 6. 教材版本与关键词没有稳定分离（优先级 P2）

“帮我找同济第七版高数教材，40元以内”两轮均无结果。模型将“同济第七版高数教材”拼成一个关键词，没有填写版本字段。实际商品的标题、版本各自满足要求，但完整拼接词不连续出现在单个字段中，后端子串匹配失败。

诊断对照中，“帮我找高数教材，版本同济第七版，40元以内”和“高数教材，同济第七版，预算40元”均正确返回同一件 20 元教材。这确认了问法结构会影响计划分解和召回。

对应主场景：`search-12`；对应诊断：`diagnostic-version-separated`、`diagnostic-version-subject`。

### 7. 相对预算修改不稳定（优先级 P2）

前置上限为 100 元时，“再便宜20元”第一轮正确改为 80 元，第二轮变为澄清。另重复三次，都返回澄清；“把预算上限改成80元”对照成功。

五次相同追问中，一次成功、四次未执行。失败时模型直接输出 `clarification`，没有进入服务端金额调整。提示词对“再便宜”与“明确新的金额”的规则需要区分用户指定的减额和没有金额的模糊要求。

对应主场景：`refine-price-01`；对应诊断：`diagnostic-cheaper-1/2/3`、`diagnostic-explicit-price`。

## 尚未实现的常见扩展需求

这 5 项单列，没有混入已有能力的通过率：

| 请求 | 当前表现 | 原因 |
| --- | --- | --- |
| 按价格从低到高排 | 要求澄清 | 查询计划与后端没有对应排序参数 |
| 只给我最便宜的一个 | 要求澄清 | 缺少最便宜选择及结果数量控制 |
| 找键盘，不要机械的 | 仍返回机械键盘 | 没有排除条件表达和执行能力 |
| 宿舍熄灯后想看书，有什么能照明的东西？ | 要求用户说出商品类型 | 模型推断台灯，但原文关键词检查不允许用途推断 |
| 罗技K380那款的详情 | 要求指出展示顺序 | 计划模型只知道展示数量，不知道商品名称，不能解析名称指代 |

其中部分回复主动建议用户“按价格”继续筛选，但系统缺少排序实现。产品文案应与实际支持的操作保持一致。

## 修复建议与验收顺序

1. 先修预算保护：保留模型正确理解且有原文依据的金额；统一“元／块／yuan”和中文数字；换商品时处理否定的旧目标，不能用不完整的解析结果覆盖已明确的预算。
2. 明确支持同义取消表达和硬条件改为偏好；接受经过验证的语义动作，避免只增加几个固定句子后继续出现同类问题。
3. 执行计划中的页码，统一翻页与条件变化判定；验证“继续”“还有其他的吗”“第二页”实际返回后续商品而不是重复卡片。
4. 统一真实 API 与 Mock 的成色语义，明确支持“以上”；把商品类型、版本和其他属性拆成独立字段，减少复合关键词漏召回。
5. 相对预算金额由服务端按已有上限计算并校验；提示词允许“已知上限减去明确金额”，不自行猜测“便宜一点”的幅度。
6. 再扩展排序、最便宜选择、排除属性、用途查找和名称指代。新增能力同时增加查询契约和后端执行，不能只让模型在文字里答应。

本轮只新增评测脚本、问法集、记录和报告，没有修改线上 Agent 行为。修复后应先保证上述稳定失败例通过，并再次用真实模型和真实 API 执行主评测；原有 127 项单元/集成测试也应继续通过。
